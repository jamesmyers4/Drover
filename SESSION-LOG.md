# SESSION-LOG.md — Drover build history

A chronological, dated record of each build session: what shipped, and the
decisions CONTEXT.md left open that got resolved along the way (with the
one-line rationale for each, since several are non-obvious). This is the
project's append-only history — CLAUDE.md is the living, as-built map of
*current* architecture and decisions; this file is how it got there and
why, in the order it happened. `GAPS.md` (and `TREELINE-GAPS.md`) track
still-open blind spots separately from this history.

Formerly split across `BUILD-STATE.md` (current status + dated decisions
log + session history) and this file; folded into one place on
2026-07-25 once Sessions 5 and 6 were both confirmed complete, per a user
request to stop maintaining a separate "current status" file once the
build was far enough along that git history plus this log covers the same
ground.

## Session 1 — 2026-07-23

Repo scaffold: all core types, the `DroverDb` SQLite layer with migrations,
project tracking files. 9 passing tests.

- Linter is **Biome** (not ESLint) — single fast tool, format + lint in one, zero plugin sprawl.
- `better-sqlite3` pinned to **^12.11.1**, not v13 — v13 dropped prebuilt binaries (install script is bare `node-gyp rebuild`) and this machine has no MSVC C++ toolchain; v12 ships prebuilds for Node 24 (ABI 137). Do not bump to v13 unless a toolchain appears.
- Both finding tables carry a `match_key TEXT NOT NULL` column and `finding_status_history` is keyed `(match_key, run_id)` — gives status history a stable cross-run join key from day one. The _computation_ of the key (planned: type + normalized route + target identifier) was Session 4's job; until then callers supplied it.
- IDs are UUIDs (`newId()` in `src/db/database.ts`); callers supply IDs for all entities _except_ action events — `insertActionEvent` generates and returns the id (the `ActionEvent` interface from CONTEXT.md has no id field, and findings need the id to reference the event).
- Package is ESM (`"type": "module"`), Node >=20, strict tsconfig with `exactOptionalPropertyTypes` — DB read helpers omit optional fields rather than returning `undefined`-valued keys, so round-trips are `toEqual`-exact.
- Session-frequency run dimension named `sessionsPerPersonaPerWeek`; run statuses `running|completed|budget-stopped|crashed`, session statuses `running|completed|hard-stopped|budget-capped` — CONTEXT.md implied but didn't enumerate these.
- In-session finding types enumerated as `console-error|http-failure|action-budget-exhausted|hard-stop`; cross-session as `duplicate-label|repeated-stumble-route|slow-checkpoint|recurring-dead-end` (from CONTEXT.md prose). Enforced by CHECK constraints — extending the list means a new migration.

## Session 2 — 2026-07-23

Browser harness (`BrowserSession` + device emulation + observation
listeners + screenshot util), treeLine adapter with real
`@treeline/acquire` integration (stub fallback), fixture site, smoke
script writing real events to SQLite. 24 tests passing.

- **treeLine loads via runtime dynamic import, not package.json** — `createTreelineAdapter()` imports `../treeLine/packages/acquire/dist/index.js` (override with `DROVER_TREELINE_PATH`), falls back to a stub that throws `TreelineUnavailableError` for login/seed-resolution and keeps a local password-field heuristic for `detectAuthWall`. Rationale: `@treeline/acquire` is unpublished; a `file:` dep would break `npm install` for adopters without the sibling checkout. See `TREELINE-GAPS.md`.
- Event stream action types — primitives `navigate|click|fill|read-page`, observations `console-error|page-error|http-failure`, plus `action-error` when a primitive throws (attempt is logged with its reasoning, then an `action-error` event, then rethrow — caller decides retry vs hard stop). Observation events carry a synthetic one-sentence `reasoning` with the truncated message; the observed URL/status lives in `target`.
- HTTP responses ≥ 400 are logged as `http-failure` events (threshold configurable per session) — log raw, filter later; only 5xx becomes an in-session _finding_ (Session 3).
- `fill` values never enter the event log (only the selector) — keeps credentials/PII out of SQLite regardless of what a persona types.
- Device emulation presets are pinned in `src/browser/device.ts` (desktop 1280×720, Pixel-7-class mobile, iPad-class tablet) rather than referencing Playwright's device registry by name — stable across Playwright upgrades.
- Playwright pinned as a regular dependency (chromium installed via `npx playwright install chromium`); `tsx` devDep powers `npm run smoke`.
- Fixed a config bug while touching lint later (Session 3): `biome.json`'s `files.includes` never listed `scripts/**`, so `npm run lint`/`lint:fix` silently skipped `scripts/smoke.ts`.

## Session 3 — 2026-07-23

Actor tier (`src/actor/`): perceive→decide→act loop, Anthropic provider
with structured tool-use output + prompt caching, trait-shaped behavior
(patience→retries/pacing, techSavviness→prompt framing, familiarity→
treeLine route map), checkpoint detector DSL, budget accounting with
soft-cap enforcement, in-session findings with screenshots, dataPolicy
enforcement. 46 tests passing; real-model smoke script written but not
run (no API key/`ant` CLI in this environment).

- `@anthropic-ai/sdk` (^0.114.0) added as a regular dependency. Actor tier default model is `claude-haiku-4-5` (`DEFAULT_ACTOR_MODEL`), per CONTEXT.md's model routing table — this overrides any general "default to Opus" guidance since it's the project's own explicit spec, not a generic choice.
- Persona traits `patience`/`techSavviness` are treated as **0..1 normalized** — CONTEXT.md types them as bare `number` with no range. `patience` → `maxRetries = round(1 + patience*4)` (bounds retries) and `pacingMs = round((1-patience)*500)` (a small wait between actions, skippable via `disablePacing` for tests/smoke). This convention is documented in `README.md`'s "Writing a domain pack" section.
- Checkpoint detector DSL finalized as `kind:value` — `url:<substring>`, `selector:<css>`, `text:<substring, case-insensitive>` (`src/actor/checkpoint.ts`, documented in `README.md`). Detector strings are never shown to the persona; only `Checkpoint.description` is, in the static system prompt's milestone list.
- Perception (`capturePerception` in `src/actor/loop.ts`) reads `BrowserSession.page` directly rather than calling `readPageState`, so perceiving doesn't itself emit a `read-page` event before every decision — only the actual chosen action (navigate/click/fill) gets logged, keeping the event log to real actions.
- Structured decision output is a forced Anthropic tool call (`tool_choice: {type:"tool", name:"decide_action"}`), flat schema (`actionType` enum + optional `url`/`selector`/`value`/`outcome`), never free text. Malformed tool input throws `MalformedDecisionError`, caught by the loop's own patience-bounded retry, same as an execution failure.
- Prompt caching applied via `cache_control: {type:"ephemeral"}` on the static system block only (domain pack + archetype + checkpoint descriptions + optional route map) — the per-action user block is never cached. Below Haiku 4.5's ~4096-token minimum cacheable prefix, this silently just doesn't cache (no error) — expected for the toy example, worth watching once real domain packs make the static block bigger.
- `assertDataPolicyAllowed` enforces `restricted` dataPolicy against an approved-provider allowlist (at the time, just `["anthropic"]` — Ollama came later, Session post-S5). Called at actor-loop construction time this session; Session 4's orchestrator moved it to config-load time.
- In-session finding `matchKey` stayed provisional this session (`computeProvisionalMatchKey` in `src/actor/findings.ts`): `${type}:${normalizedTarget}`, stripping query/hash from URL-shaped targets. Session 4 owns the real cross-run matching key.
- `action-budget-exhausted` only fires when the goal's action budget is actually exhausted (the `while` loop's own exit), not when the persona's `finish` decision voluntarily ends the goal early (e.g. `outcome: "gave-up"`) — the two are behaviorally different but CONTEXT.md's four finding types have no "gave up early" type; logged as a candidate for a fifth type if real runs show it's worth distinguishing.
- Checkpoint detector DSL is intentionally minimal: the three matchers (`url:`, `selector:`, `text:`) are substring/existence checks only — no regex, no visibility vs. presence distinction, no combining multiple conditions into one checkpoint (AND/OR). A real domain pack may need one of these later and should extend the DSL then rather than working around it with extra checkpoints.

## Session 4 — 2026-07-23

Discovery-mode orchestrator (`src/orchestrator/`): schedule expansion,
weighted goal draw, real cross-run `matchKey` (moved to shared
`src/matching/`), finding status reconciliation, run-level budget
ceiling, per-session isolation (hard-stop and exceptions alike),
domain-pack teardown hook (new field), `drover run` CLI. 72 tests
passing (26 new); CLI smoke-tested end-to-end as a real subprocess
against the fixture site.

- Real cross-run `matchKey` lands in a new shared module, `src/matching/match-key.ts` (`computeMatchKey`/`normalizeRoute`), not inline in `src/actor/findings.ts` where Session 3's provisional version lived — both the actor tier (finding creation) and the orchestrator (reconciliation, and later the analyst tier) need the identical formula. Format: `${type}:${normalizedRoute}` optionally suffixed `:${method}` when an HTTP method is embedded in the target string (`"500 GET http://..."` from `src/browser/session.ts`'s observation listeners) or explicitly supplied. `normalizeRoute` drops origin, query, and hash — deliberately host-independent so the same route matches across runs even if a dev/staging URL's port changes.
- `DomainPack` gained an optional `teardown?: (ctx: DomainPackTeardownContext) => Promise<void>` field (`src/types/domain-pack.ts`) — CONTEXT.md's schema block doesn't define one verbatim, but "Environment & safety" requires a "config-declared cleanup hook per domain pack" that "runs even after budget-stop or crash," so this was added as the natural extension point. `DomainPackTeardownContext` is just `{ runId, targetBaseUrl }` — see `GAPS.md` for the follow-on gap (no record of which app-side rows a run actually created, so a pack author's teardown has to self-correlate).
- Schedule iteration order is **week-major** (`src/orchestrator/schedule.ts`: all of week 1's sessions across every simulated org member, before any of week 2's), not persona-major. CONTEXT.md doesn't specify an order, only that execution is sequential — week-major was chosen because it more faithfully simulates "an org's activity over N weeks" than batching one persona's entire tenure first. `orgSize` simulated org members are round-robin assigned one archetype each from `domainPack.personas` (a pack ships far fewer archetypes than a simulated org has people); instance numbers (`p1#1`, `p1#2`, ...) stay stable for the same member across weeks.
- The run-level hard dollar ceiling is checked **between** sessions only (top of the schedule loop, before starting the next session), never mid-session — matches CONTEXT.md's "finish the in-flight write... never dies mid-write" and falls out naturally from sequential execution: a session's own DB writes always complete (success or hard-stop) before the next budget check. If the final scheduled session's cost happens to tip the running total over the ceiling, the run still reports `completed` (the full schedule finished) rather than `budget-stopped` — `budget-stopped` means the schedule was cut short, not "spend happened to land at or above the ceiling at the end."
- Finding status reconciliation (`src/orchestrator/reconcile.ts`) scopes "prior runs" to the same `DomainPack.appName` via a SQL join through `runs` (finding_status_history has no app_name column of its own — added `DroverDb.getPriorMatchKeysForApp` / `getLatestStatusForMatchKeyExcludingRun`). A match_key already `resolved` is left alone on subsequent absent runs rather than re-flagged every time — avoids resolved-record spam for a finding that stays fixed across many runs. Discovered mid-session: `recorded_at` (caller-supplied `Date.now()`) can tie across back-to-back runs in fast automated execution (tests, scripted batches), so both `getStatusHistory` and `getLatestStatusForMatchKeyExcludingRun` add SQLite's implicit `rowid` as a secondary sort key — true insertion order, immune to wall-clock resolution ties.
- CLI (`src/cli/index.ts`, `drover run <domain-pack> [--config sim.config.ts] [--out path]`) built on `commander` (added as a regular dependency). Domain packs and sim configs are loaded as plain TS modules with a **default export** (`src/orchestrator/config-loader.ts`'s `loadDefaultExport`) — `tsx` was promoted from a devDependency to a regular dependency because the compiled CLI (`dist/cli/index.js`, the `bin` target) needs `tsx/esm/api`'s `register()` at runtime to dynamically `import()` a user's `.ts` config file; calling `register()` is a no-op-safe try/catch when the process is already running under `tsx`.
- Per-session isolation in the orchestrator covers two distinct failure shapes identically (both end the session `hard-stopped` and continue the batch): the actor loop's own `hard-stopped` result (patience-bounded retries exhausted), and an exception escaping `BrowserSession.open`/`runPersonaSession` entirely (browser crash, unexpected error — counted separately in the result as `sessionsErrored` vs. `sessionsHardStopped`). Only an error escaping the _scheduling loop itself_ (e.g. a schedule referencing a goal id absent from `domainPack.goals` — a config bug, not a runtime persona failure) marks the whole run `crashed`; teardown and reconciliation still run first (finally-style) before the error is rethrown to the CLI.
- No real Anthropic credentials in this build environment — `npm run smoke:orchestrator` still runs the actual CLI process end-to-end (spawns `drover run` via tsx's bundled CLI loader against the fixture site), but every session's `AnthropicModelProvider` construction throws immediately for lack of an API key, which the orchestrator's per-session isolation catches as a hard-stop — so the smoke run proves the full scheduling/budget/teardown/reconciliation pipeline and produces a populated SQLite file, just not real model behavior. `runDiscovery`'s own logic (scheduling, hard-stop survival, budget-stop, crash+teardown, reconciliation) is fully covered without needing credentials by `tests/orchestrator/run-discovery.test.ts`'s real-browser + `ScriptedModelProvider` integration tests.

## Session 5 — 2026-07-23

Analyst tier (`src/analyst/`): per-session digests with derived metrics,
single-shot Sonnet Batch API call (real `BatchAnalystProvider`,
create/poll/results lifecycle), structured-output validation (unknown
enum values and hallucinated session ids get filtered/skipped, never
crash), `cross_session_findings` writes with borrowed representative
evidence, `drover analyze <run-id>` CLI command. Made
`finding_status_history` upsert-safe so the analyst's second
reconciliation pass can correct the orchestrator's earlier partial one.
94 tests passing (22 new); real-model smoke script written but not run
(no API key/`ant` CLI in this environment) — CLI wiring manually verified
up to the point of the missing-credentials error.

- **`DroverDb.recordFindingStatus` changed from insert-only to an upsert** (`ON CONFLICT(match_key, run_id) DO UPDATE` — `src/db/database.ts`). Root cause: the orchestrator (Session 4) already reconciles a run's findings right after it finishes, but at that point only in-session findings exist — cross-session findings don't exist until the separate, later `drover analyze` command runs (run and analyze are deliberately decoupled so a run can be re-analyzed without re-simulating). Without the upsert, a cross-session-typed match_key that's still recurring but not yet re-detected by the analyst would get permanently mis-tagged `resolved` by the orchestrator's first pass, and `runAnalyst`'s second reconciliation call would then hit a primary-key violation trying to correct it. The upsert makes `reconcileRunFindings` safely re-runnable per run.
- Analyst tier is **one Batch API call per `drover analyze` invocation**, covering every session in the run in a single prompt (not one call per session) at first — CONTEXT.md doesn't specify batch granularity, and a single run's session count seemed small enough in v1's initial target use cases that one prompt covering all digests was simpler. (Chunking arrived later, in the post-Session-5 fix round below.)
- `computeCostUsd` (from `src/actor/budget.ts`, reused as-is) doesn't know about Batch API's 50% discount, so `BatchAnalystProvider` applies a `BATCH_DISCOUNT = 0.5` multiplier itself after calling it (`src/analyst/provider.ts`) rather than teaching the shared budget module about batch pricing — the discount is specific to how the analyst tier calls the API, not a property of the model/pricing table itself.
- A cross-session finding's optional evidence (`screenshotPath`/`traceSnippet`) is **borrowed, not newly captured** — the analyst has no live browser (it's a post-hoc SQLite-only read), so `findRepresentativeEvidence` (`src/analyst/analyze.ts`) takes the first available screenshot from any of the finding's referenced sessions' own `in_session_findings`, if one exists. Best-effort only; a cross-session finding with no matching in-session evidence anywhere just ships without a screenshot, consistent with CONTEXT.md's "Visual evidence" section.
- `drover analyze` takes a **required `--db <path>`** flag (`src/cli/index.ts`) rather than any default — unlike `drover run`, which picks a default `runs/<timestamp>.sqlite` output path, a run id alone doesn't say which SQLite file it lives in, so there's no sensible default to fall back to. The `Run` row's own `config` snapshot (stored by `drover run`) supplies the analyst-tier `ModelRoute` for the CLI, so `analyze` doesn't need a second `--config` flag.

## Post-Session-5 fixes — 2026-07-23 to 2026-07-24

A run of GAPS.md fixes landed between Sessions 5 and 6, each closing a
logged gap (and usually opening a narrower one in its place):

- **`SimConfig.concurrencyCap > 1` was first rejected instead of silently ignored** — `runDiscovery` validated `concurrencyCap` before writing the run row, alongside `assertDataPolicyAllowed`; anything above 1 threw `ConcurrencyNotImplementedError`. (Superseded by real bounded concurrency below.)
- **`ActionEvent.checkpointId` is now populated.** The actor loop (`src/actor/loop.ts`) re-evaluates checkpoints immediately after a primitive action succeeds and tags that action's event via a new `DroverDb.updateActionEventCheckpoint` (an UPDATE, not part of `insertActionEvent` — satisfaction is only knowable after the action's effect lands on the page, one step after the event row is written).
- **`reconcileRunFindings` no longer writes a premature `resolved` tag for cross-session findings during `runDiscovery`'s post-run pass.** New `ReconcileOptions.crossSessionDataComplete` flag (default `true`). `runDiscovery`'s post-run call explicitly passes `crossSessionDataComplete: false`: at that point `drover analyze` hasn't run yet, so `getCrossSessionFindingsByRun(runId)` is always empty by construction, not because a pattern actually stopped recurring. The first pass now simply skips cross-session-typed match_keys entirely when the flag is false, leaving their status untouched until the analyst's own reconciliation call (which keeps the default `true`). This makes `drover run`'s printed reconciliation summary accurate immediately rather than only after `drover analyze` also runs. Residual: a cross-session-typed match_key's `new`/`still-open` status still can't be assigned until `drover analyze` actually runs and re-detects the pattern — there's no data to tag it with before that.
- **Persona trait numeric range gap closed** — already resolved by an earlier README pass (a "Writing a domain pack" section documenting the 0..1 convention), just not reflected in `GAPS.md`/`CLAUDE.md`'s wording at the time; only the stale phrasing needed fixing, not the behavior.
- **`reasoning` length is now schema-hinted and enforced by truncation, not left as an unenforced prompt convention.** `DECIDE_TOOL.input_schema.properties.reasoning` (`src/actor/provider.ts`) gained `maxLength: MAX_REASONING_LENGTH` (200) plus a description telling the model to stay under it; `parseDecision` truncates (appending `…`) any `reasoning` string longer than that limit rather than leaving it unbounded. Deliberately a soft truncation, not a new parse-error case: "one sentence per action" is a prompt-adherence goal, not a correctness invariant, so failing the whole decision over verbosity alone would be the wrong trade-off.
- **The analyst tier gained an optional hard cost ceiling, checked pre-flight.** `BudgetConfig` gained `analystCeilingUsd?: number`. Unlike the actor tier's `SessionBudget` (checks a soft cap between calls in a loop), the analyst tier makes exactly one all-or-nothing Batch API call — it's billed the instant it's submitted, so a check-after-the-fact cap can't prevent overspend on that same call. `src/analyst/budget.ts` (`estimateAnalystCostUsd`/`estimateTokens`/`AnalystBudgetExceededError`) estimates a worst-case cost from the assembled prompt (chars/4 proxy at first) and the Batch request's `max_tokens` ceiling, Batch-discounted the same as the real call; `runAnalyst` checks it before creating/calling the provider.
- **The cost of a malformed `decide_action` call is now recorded against budget.** Previously `AnthropicModelProvider.decide()` only computed `usage`/`costUsd` after `parseDecision` succeeded, so a malformed tool call — still billed by Anthropic — threw before its cost was ever returned, and `SessionBudget`/`totalCostUsd` under-reported real spend. Fixed by computing `billedUsage` from `response.usage` unconditionally, right after the API response comes back and before the tool-call payload is parsed; `runPersonaSession`'s retry catch block now records that cost before continuing the retry loop.
- **The analyst tier's digest gained true per-checkpoint reach times from `ActionEvent.checkpointId`**, instead of only a whole-session-duration-by-goal proxy. `SessionDigest` gained `checkpointReachTimesMs: Record<checkpointId, elapsedMs>` (first-reach-wins); the analyst prompt renders this as a per-session "Checkpoint reach times" block. Residual: the analyst still only sees the raw checkpoint id string, no description or goal context yet (closed next).
- **`OllamaModelProvider` added — the actor tier's second real `ModelProvider`, closing the "no local/self-hosted provider" gap.** Calls a local/self-hosted Ollama server's `/api/chat` endpoint with an OpenAI-style `tools` array framing the same `decide_action` schema Anthropic uses, parsed by the same shared `parseDecision`. Base URL defaults to `http://localhost:11434`, overridable via `OLLAMA_HOST` or an explicit constructor arg. Cost is hardcoded to `$0` (no per-token billing for a local model). `"ollama"` added to `APPROVED_RESTRICTED_PROVIDERS` — CONTEXT.md names a fully local model as the explicit zero-exposure alternative for `restricted` packs. Never exercised against a real local Ollama server (none was available in this build environment) — see `GAPS.md`.
- **`estimateAnalystCostUsd` now counts real input tokens via Anthropic's `messages.countTokens` endpoint**, falling back to the chars/4 heuristic only when that's unreachable. `estimateAnalystCostUsd` is now `async` with an injectable `TokenCounter`; the real counter's Anthropic client is constructed lazily inside the counter's closure so a missing API key surfaces as a rejected promise (catchable), not a synchronous throw. The real endpoint path itself has never run end-to-end in this build environment (no credentials) — every test exercises the fallback path instead.
- **Checkpoint ids are no longer opaque to the analyst tier — `Run.checkpointContext` snapshots each id's owning goal and description at run-creation time.** `Run` gained an optional `checkpointContext?: Record<checkpointId, CheckpointContextEntry>` (`CheckpointContextEntry = { goalId, description }`), built by `buildCheckpointContext(domainPack)` (`src/orchestrator/run-discovery.ts`) at run-creation time — taken then, not re-read live at `drover analyze` time, since the pack file could change or move between the two commands and `runAnalyst` only ever holds the run's stored `SimConfig` snapshot. Stored via migration version 2 (`checkpoint_context_json` column, nullable). `buildAnalystUserPrompt` renders `cp-signup-complete ("User submits the signup form", goal: signup-flow): 4200ms` when context is available, falling back to the bare id otherwise. Residual: still no position-within-goal ordering context (e.g. "2nd of 4 checkpoints").
- **Real bounded concurrency implemented — `runDiscovery` no longer only has a sequential path.** `ConcurrencyNotImplementedError` is gone; `runDiscovery` runs a bounded worker pool whenever `concurrencyCap` is set above 1: `workerCount = max(1, min(concurrencyCap, schedule.length))` workers, each repeatedly claiming the next unclaimed schedule entry via shared `nextIndex`/`stopLaunching` closures (safe without locking — Node never preempts mid-synchronous-block). `concurrencyCap` 1 (or unset) still runs exactly one worker, identical to the old sequential loop. A new `InvalidConcurrencyCapError` replaces the old rejection error, now validating shape (must be a positive integer) rather than rejecting any value above 1. Residual: the run-level cost ceiling becomes best-effort, not exact, above `concurrencyCap` 1 — up to `concurrencyCap - 1` other sessions can already be in flight by the time a worker notices the ceiling was crossed.
- **Analyst request chunking — a large run's session digests are split across multiple concurrent Batch requests instead of one prompt covering every session.** `runAnalyst` groups digests into chunks of at most `sessionsPerChunk` (`DEFAULT_SESSIONS_PER_CHUNK = 25`, a guessed round number, not derived from real Horse Haven Ops run data), one `provider.analyze()` call per chunk, concurrently via `Promise.all`. The pre-flight `analystCeilingUsd` check sums every chunk's estimate before submitting any of them. `drover analyze` gained `--sessions-per-chunk <n>`. Residual, inherent to chunking at all: cross-session correlation only ever happens _within_ a chunk — a pattern spanning sessions in two different chunks is invisible to `drover analyze` regardless of chunk size.

## Session 6 — 2026-07-24

Reporting (`src/report/`) reads a completed run's SQLite data only — no
re-simulation, no re-analysis, same "separate CLI command" precedent
`drover analyze` established over `drover run`. `buildRunReport` merges
`in_session_findings` and `cross_session_findings` into one row per
`matchKey` (safe because the type enums never overlap), attaches each
row's current-run status from a new `DroverDb.getStatusHistoryForRun`,
and groups rows by every goal any contributing session belongs to for
the "breakdown by flow" section. `renderMarkdownReport` turns that into
a findings summary table, a per-flow breakdown, run metadata (dimensions
+ actual actor/analyst spend vs. budget), a "since last run"
new/still-open/resolved count, and a separate evidence appendix
(screenshot paths, event ids — never inlined into the summary tables).
`drover report <run-id> --db <path> [--out report.md]` is the new CLI
command; no `--out` prints to stdout. 156 tests passing (11 new); no
credentials were needed for this tier (pure SQLite read, no model
calls).

- **`Run.actorCostUsd`/`Run.analystCostUsd` added (migration 3) so `drover report` can show real cost actuals vs. budget.** Neither cost was persisted anywhere before this — `RunDiscoveryResult.totalCostUsd` (Session 4) and `RunAnalystResult.costUsd` (Session 5) were both in-memory return values of their respective CLI invocations, gone once the process exited, so a later `drover report` process (reading only the SQLite file, same as `drover analyze` already does for its config) had nothing to read. `actorCostUsd` is a plain overwrite (`DroverDb.updateRunActorCost`, called once at the end of `runDiscovery`) since exactly one `drover run` invocation ever writes a given run row's actor spend. `analystCostUsd` is additive (`DroverDb.updateRunAnalystCost`, `SET analyst_cost_usd = COALESCE(analyst_cost_usd, 0) + ?`) since a run can be re-analyzed via multiple separate `drover analyze` invocations and each one bills real additional cost — the stored value is the cumulative total across every pass, not just the most recent one.
- **Findings from both tables merge into one row per `matchKey`, not rendered as two separate lists.** `buildRunReport` (`src/report/report.ts`) iterates `in_session_findings` (via each session) and `cross_session_findings` (via the run) into the same `Map<matchKey, FindingReportRow>` — safe because `computeMatchKey` embeds the finding type in the key itself and the in-session/cross-session type enums never overlap, so a collision between the two kinds on the same key is structurally impossible. A row's `status` comes from a new `DroverDb.getStatusHistoryForRun(runId)` (filtered by `run_id`, not `match_key` — the existing status queries are both matchKey-first, the wrong shape for "every status this run recorded"). One asymmetry worth knowing: a `finding_status_history` row can say `resolved` for a match_key that has no row in `findings` at all — reconciliation writes `resolved` exactly when a match_key was open going into the run and wasn't seen this run, so there's no current-run finding to attach the tag to. `reconciliation.resolved` (the "since last run" count) still includes it; the `findings` list just doesn't have a row for it, since that list is fundamentally "what this run actually found."
- **"Breakdown by flow" groups by `Goal.id`**, which CONTEXT.md doesn't literally use the word "flow" for but is the closest existing concept — an in-session finding's flow is its originating session's `goalId`; a cross-session finding is attributed to every goal any of its `sessionIds` ran, so one finding can legitimately appear under more than one flow's breakdown if it was observed across sessions with different goals.
- **`hasAnalystPass` is derived from `run.analystCostUsd !== undefined`, not from whether any `cross_session_findings` rows exist for the run.** A real `drover analyze` pass that finds zero cross-session patterns is still a real analyst pass — reporting it as "no analyst pass yet" would be actively misleading.

## Session 9 (in progress) — 2026-07-26 — login/storageState wiring

Picked up as prerequisite work before Session 9's actual goal (the real Horse Haven Ops domain pack + a validation run against `volunteer.horsehaventn` staging), which remains blocked on two external inputs neither available in this build environment: staging URL/credentials, and `ANTHROPIC_API_KEY`. - **`DomainPack.auth?: DomainPackAuthCredentials`** (`src/types/domain-pack.ts`) is the new optional field, structurally mirroring `TreelineLoginCredentials` (`src/treeline/adapter.ts`) but deliberately re-declared rather than imported — `src/types/` had zero dependency on any other tier before this (every file in it only imports from within `src/types/`), and this is plain data with no treeline-specific behavior, so duplicating the shape costs nothing and keeps that leaf-module property intact. Same pattern `TreelineStorageState` itself already uses one layer down (it mirrors Playwright's `storageState()` shape without importing Playwright into the treeline adapter's own public types).
- **Deliberately on `DomainPack`, not `SimConfig`** — the one design decision this session actually had to make. `Run.config: SimConfig` is what gets persisted into the run's own SQLite row (`src/types/run.ts`); `DomainPack` never does. Putting `auth` on `SimConfig` would mean a real username/password round-tripping into the database on every run; putting it on `DomainPack` means it never does, extending the existing "secrets never enter prompt content" discipline (already applied to `fill()` values in the event log) one layer further to "or persisted state."
- **Login happens exactly once per run, not once per session.** `runDiscovery` (`src/orchestrator/run-discovery.ts`) calls `treelineAdapter.performLogin(browser, domainPack.auth)` once, right after the browser launches and before the worker-pool loop starts, storing the result in a `let storageState` that the session-launching closure (`runOneScheduledSession`) already had captured in scope. Every session's `BrowserSession.open()` call spreads it in when present. Reusing one `storageState` across a whole run's sessions is a deliberate v1 simplification (real login is a genuine network operation, potentially rate-limited) — the trade-off it accepts is documented in `GAPS.md`: a pack whose different goals need different roles/accounts can't express that yet, since every session in the run shares the same logged-in identity.
- **A login failure crashes the whole run**, same code path as `runOneScheduledSession` throwing for an unknown persona/goal id (`status = "crashed"`, `crashError` set, rethrown after teardown runs finally-style) — reasoned as: if a pack declares `auth` at all, every one of its goals is presumably unreachable without it, so there's no meaningful per-session isolation to offer the way there is for an ordinary actor-loop hard-stop. This means `sessionsScheduled` stays `0` on a login failure — no session ever gets far enough to open a browser context.
- **Test coverage**: `tests/orchestrator/run-discovery.test.ts` gained two cases. The first spies on `BrowserSession.open` (via `vi.spyOn`, since the fixture site under test has no real login page to exercise `performLogin` against for real — the test injects its own mocked `TreelineAdapter` with a stubbed `performLogin`) and asserts it's called exactly once and every session's `storageState` argument is the exact object `performLogin` resolved. The second asserts a rejected `performLogin` crashes the run, still runs teardown, still marks the run row `crashed`, and never lets `BrowserSession.open` get called at all. Building the mock `TreelineAdapter` needed one small wrinkle: `StubTreelineAdapter`'s methods live on its class prototype, not as own enumerable properties (its only own property is the `readonly kind` field initializer), so `{ ...stubAdapter, performLogin: mockFn }` would silently drop every other method — worked around by binding each method explicitly (`stubAdapter.checkAuthStillValid.bind(stubAdapter)`, etc.) into a plain object literal instead.
