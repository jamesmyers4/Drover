# GAPS.md — Drover's own blind spots

Drover shortcomings, missing capabilities, and future-improvement ideas, logged as they surface during builds and real runs (per CONTEXT.md's Learning Loop). Entries here are candidates for post-v1 work — log and move on, don't fix out of scope.

## 2026-07-24 (GAPS fix) — Checkpoint reach times now carry description/goal context, but ordering-within-goal still isn't surfaced

Previously logged as "Checkpoint reach times are keyed by opaque checkpoint id, with no description/ordering context." `Run` (`src/types/run.ts`) gained an optional `checkpointContext?: Record<checkpointId, { goalId: string; description: string }>`, snapshotted at run-creation time by `buildCheckpointContext` (`src/orchestrator/run-discovery.ts`, exported from the orchestrator barrel) from `DomainPack.goals[].checkpoints` — taken at run-creation rather than looked up live from the pack file at `drover analyze` time, since the pack file could change or move between the two commands, and `runAnalyst` only ever had the run's stored `SimConfig` snapshot, not the domain pack itself. Stored via a new `checkpoint_context_json` column (migration version 2, `src/db/migrations.ts`), nullable for backward compatibility — pre-migration runs round-trip through `DroverDb.getRun` with the field simply absent, same optionality pattern as `endedAt`. `runAnalyst` (`src/analyst/analyze.ts`) passes `run.checkpointContext` into `buildAnalystUserPrompt` (`src/analyst/prompt.ts`), which now renders `cp-signup-complete ("User submits the signup form", goal: signup-flow): 4200ms` instead of the bare `cp-signup-complete: 4200ms` whenever context is available for that id, falling back to the bare id otherwise (old runs, or a checkpoint id the context map doesn't cover). Covered by new tests: `tests/db.test.ts` (round-trip with and without `checkpointContext`), `tests/orchestrator/run-discovery.test.ts` (`buildCheckpointContext` unit tests plus an end-to-end assertion that a real `runDiscovery` call populates it correctly on the stored `Run`), `tests/analyst/prompt.test.ts` (new file — rendering with context, without context, and with a context map that doesn't cover the digest's checkpoint id), and a `tests/analyst/analyze.test.ts` case confirming the wiring end-to-end with a capturing `AnalystProvider`. What's still open: the analyst still doesn't see a checkpoint's *position* within its goal's checkpoint list (e.g. "2nd of 4 checkpoints") — only its id, description, and owning goal id. Post-v1: if a real domain pack's checkpoints benefit from ordering context (e.g. distinguishing "stuck early" from "stuck near the end"), extend `CheckpointContextEntry` with an `index`/`total` pair computed the same way `buildCheckpointContext` already walks `goal.checkpoints`.

## 2026-07-24 (GAPS fix) — Real-tokenizer analyst budget estimate hasn't been exercised against a live API

Previously logged as "Analyst-tier budget ceiling is a pre-flight estimate, not exact accounting." `estimateAnalystCostUsd` (`src/analyst/budget.ts`) now counts input tokens via Anthropic's real, free `messages.countTokens` endpoint by default (`createApiTokenCounter`, exported as the `TokenCounter` type) — counting the exact `system`+`messages` shape `BatchAnalystProvider` actually sends, not the old chars/4 proxy. The function is now `async`; `runAnalyst` (`src/analyst/analyze.ts`) awaits it. Any failure to reach the API (missing credentials, offline, a flaky request) is caught and falls back to the old `estimateTokens` chars/4 heuristic rather than blocking the pre-flight gate — this is why the existing `tests/analyst/budget.test.ts` cases still assert the old heuristic math unchanged: no `ANTHROPIC_API_KEY` is available in this build environment, so every one of those calls exercises the fallback path, not the real API path. New tests cover an injected `TokenCounter` taking precedence when it succeeds, and the fallback firing when an injected counter rejects — but the real `createApiTokenCounter` path itself (an actual `countTokens` HTTP call succeeding and returning a real count) has never run, same "written but not exercised against the real thing" situation as the actor/analyst tiers' Anthropic smoke scripts before a key was available. What's still open: run `ANTHROPIC_API_KEY=... npm test -- tests/analyst/budget.test.ts` (or a small ad-hoc script) once a key is available to confirm the real endpoint path end-to-end. (The "large-run chunking still isn't implemented" half of this entry's original text is closed — see the newer chunking entry below.)

## 2026-07-24 (GAPS fix) — Analyst request chunking only correlates patterns within a chunk, and the chunk-size default is a guess

Previously logged as (the second half of) "splitting a very large run's sessions into multiple smaller batch requests... still isn't implemented." `runAnalyst` (`src/analyst/analyze.ts`) now splits a run's session digests into groups of at most `sessionsPerChunk` (`RunAnalystOptions.sessionsPerChunk`, default `DEFAULT_SESSIONS_PER_CHUNK = 25`) and sends each group as its own `provider.analyze()` call, all issued concurrently via `Promise.all` — for the real `BatchAnalystProvider`, each chunk is its own independent `batches.create()` request (reusing the same internal `custom_id` across calls is fine; it only needs to be unique *within* one call's `requests` array, not globally). The pre-flight `analystCeilingUsd` check now sums every chunk's `estimateAnalystCostUsd` result before submitting any of them, so a run that only exceeds the ceiling once all chunks are counted still fails closed before a single request goes out (previously there was only ever one chunk, so this distinction didn't exist). `drover analyze` gained a `--sessions-per-chunk <n>` CLI flag mirroring `--poll-interval-ms`. Covered by new tests in `tests/analyst/analyze.test.ts`: one proves genuine multi-call fan-out (asserting which session ids land in which chunk's prompt, and that findings/cost from every chunk — not just the last call — get aggregated into the final result), one proves the ceiling check sums across chunks rather than checking only the first (derives its ceiling from an independently-computed single-chunk estimate rather than a guessed constant), and one guards the `sessionsPerChunk <= 0` case that would otherwise infinite-loop the chunking helper. What's still open: cross-session correlation only ever happens *within* a chunk — a pattern that would only be visible by comparing a session in chunk 1 against a session in chunk 2 is invisible to both calls, since neither model invocation ever sees the other chunk's digests. This is an inherent trade-off of chunking at all, not a bug, but worth knowing before trusting `drover analyze`'s completeness on a run whose session count is well above `sessionsPerChunk`. Also open: the default of 25 sessions per chunk is a guess (a round number "comfortably larger than any run this v1 has actually been exercised against"), not derived from a real prompt-size ceiling or real Horse Haven Ops run data — revisit once a real domain pack's typical run dimensions are known.

## 2026-07-24 (GAPS fix) — Bounded concurrency's budget ceiling is best-effort, not exact, above concurrencyCap 1

Previously logged as "`concurrencyCap` above 1 is still not real concurrency, just rejected cleanly." `runDiscovery` (`src/orchestrator/run-discovery.ts`) now implements real bounded concurrency: a worker-pool scheduler (`workerCount = min(concurrencyCap, schedule.length)` workers, each repeatedly claiming the next unclaimed schedule entry) replaces the old plain `for` loop. `concurrencyCap` 1 (or unset, the default) runs exactly one worker — behaviorally identical to the old sequential loop, confirmed by the existing test suite passing unchanged. `ConcurrencyNotImplementedError` is gone; `concurrencyCap > 1` is no longer rejected. A new `InvalidConcurrencyCapError` replaces it for a genuinely invalid value (0, negative, fractional, NaN) — still checked before `db.insertRun`, same timing/pattern as before. Per-session isolation is unaffected: each worker's per-session try/catch is unchanged, so a hard-stop or browser crash in one concurrent session still doesn't take down the others; only an error escaping the persona/goal lookup itself (a schedule/config bug) still crashes the whole run, now by setting a shared `stopLaunching` flag so every worker stops claiming new work before the error propagates. Playwright's `browser.newContext()` is safe to call concurrently (confirmed via `BrowserSession.open`'s existing per-session context isolation) and `better-sqlite3` calls are synchronous, so no explicit locking was needed for either. New test in `tests/orchestrator/run-discovery.test.ts` proves *real* overlap (not just that a cap above 1 no longer throws): a custom `ModelProvider` that blocks for a fixed delay on its one `decide()` call, tracking peak concurrent in-flight calls across 6 scheduled sessions at `concurrencyCap: 3` — asserts `maxActive > 1`, which is only possible if sessions genuinely ran at the same time. What's still open: the run-level cost ceiling is now a best-effort check, not an exact one, whenever `concurrencyCap > 1` — up to `concurrencyCap - 1` other sessions can already be in flight (and add their own cost) by the time a worker notices the ceiling was crossed and stops launching new work, since the check only happens before *launching* a new session, not continuously. `concurrencyCap` 1 still preserves the old exact-ceiling guarantee. Post-v1: if a real domain pack run shows this overshoot matters in practice (e.g. a tight ceiling with a high cap), consider a stricter "reserve" scheme (provisionally counting a session's max possible per-session cost against the ceiling the moment it's launched, refunding the difference once its real cost is known) — not implemented here since it adds real complexity for a v1 that already documents the trade-off.

## 2026-07-24 (GAPS fix) — Ollama provider's tool-calling support hasn't been exercised against a real local server

Previously logged as "No local/self-hosted provider for `restricted` domain packs." `OllamaModelProvider` (`src/actor/provider.ts`) now implements `ModelProvider` against Ollama's `/api/chat` endpoint with an OpenAI-style `tools` array (same `decide_action` schema as the Anthropic path, reusing the shared `parseDecision`), and `"ollama"` was added to `APPROVED_RESTRICTED_PROVIDERS` — CONTEXT.md names it explicitly as the zero-exposure option, and nothing leaves the machine running it, so it carries the same data-handling assurance as Anthropic for a `restricted` pack. Cost is hardcoded to `$0` (no per-token billing for a local model, so it deliberately doesn't run through `computeCostUsd`/`PRICING`). A model with no tool-calling support just yields a `MalformedDecisionError` per attempt (same treatment as Anthropic's "no tool_use block" case), not a crash. Covered by 8 new tests in `tests/actor/provider.test.ts` mocking global `fetch` (no real Ollama install needed to test the wiring). What's still open: this has never been run against a real local Ollama server — no Ollama install was available in this build environment, same "written but not exercised against the real thing" situation as the actor/analyst tiers' Anthropic smoke scripts before a key was available. Also unverified: how well small local models (the realistic choice for a "zero-exposure, low-cost" use case) actually follow the forced-tool-call/JSON-schema contract in practice — the Anthropic path gets a real `tool_choice` force, but Ollama's tool calling is best-effort per-model, so a weak local model may produce a much higher `MalformedDecisionError` rate than Haiku does. Post-v1: exercise against a real Ollama install once available, and if the malformed-rate turns out high in practice, consider adding a smoke script (`npm run smoke:actor:ollama`?) mirroring the existing pattern.

## 2026-07-23 (S3) — Checkpoint detector DSL is intentionally minimal

`src/actor/checkpoint.ts`'s three matchers (`url:`, `selector:`, `text:`) are substring/existence checks only — no regex, no visibility vs. presence distinction, no combining multiple conditions into one checkpoint (AND/OR). Fine for the toy example and Session 3's tests; Session 8's real Horse Haven Ops pack may need one of these and should extend the DSL then rather than working around it with extra checkpoints.

## 2026-07-24 (post-S5, GAPS fix) — `drover run`'s reconciliation pass no longer needs an ordering dependency on `drover analyze` to be correct

Previously logged as "Cross-run reconciliation is two-phase and can be transiently wrong for cross-session findings." `reconcileRunFindings` (`src/orchestrator/reconcile.ts`) gained a `ReconcileOptions.crossSessionDataComplete` flag (default `true`). `runDiscovery`'s post-run call now explicitly passes `crossSessionDataComplete: false`: at that point in the pipeline, `drover analyze` hasn't run yet, so `getCrossSessionFindingsByRun(runId)` is always empty by construction — not because the pattern actually stopped recurring. Previously this made the absent-match_key loop mark any prior open cross-session-typed match_key `resolved`, a tag that was only corrected later by `runAnalyst`'s second reconciliation call (relying on the S5 upsert fix to survive being written twice). Now the first pass simply skips cross-session-typed match_keys entirely (leaves them at whatever status they already had) when `crossSessionDataComplete` is false, so no premature `resolved` tag is ever written to `finding_status_history` in the first place, and the console summary `drover run` prints is accurate immediately rather than only after `drover analyze` also runs. In-session-typed match_keys are unaffected — those are fully known right after a run finishes, so they're still resolved/still-open/new'd in the same single pass as before. Covered by two new cases in `tests/orchestrator/reconcile.test.ts` ("leaves a prior open cross-session-typed match_key untouched when crossSessionDataComplete is false" / "still resolves an absent in-session-typed match_key even when crossSessionDataComplete is false"). What's still open: this only prevents _false_ resolutions — it doesn't change the fact that a cross-session-typed match_key's `new`/`still-open` status still can't be assigned until `drover analyze` actually runs and re-detects the pattern (there's no data to tag it with before that). A domain pack that never runs `drover analyze` after `drover run` will simply never get cross-session findings reconciled at all, which is expected (analyze is what produces the data reconciliation acts on) but still worth flagging explicitly once Session 6's reporting work exists, per the original entry's suggestion.

## 2026-07-23 (S4) — Domain pack teardown hooks have no record of what a run created

`DomainPack.teardown` (added this session, `src/types/domain-pack.ts` — not in CONTEXT.md's verbatim schema, see BUILD-STATE.md decisions log) is called with only `{ runId, targetBaseUrl }`. It has no list of the actual records/rows a run's personas created (signups, schedule edits, etc.) — CONTEXT.md's "staging teardown wipes everything a run created" assumes the pack author has _some_ way to correlate created data back to a run. As built, that correlation is entirely the pack author's responsibility (e.g., tagging synthetic form data with the runId at fill-time, or a timestamp-window sweep) — Drover doesn't track "which app-side records this run touched" anywhere. Worth revisiting once a real domain pack (Session 8's Horse Haven Ops pack) actually needs to implement a non-trivial teardown and finds out whether `runId` alone is enough.
