## 2026-07-29 — `DomainPack.auth` couldn't express Horse Haven Ops' real login (Clerk, no password) — RESOLVED 2026-07-29

Found doing `SESSION-10-PLAN.md`'s Session 3 (extending `packs/horse-haven-ops/domain-pack.ts` past `/kiosk`). Every other route (`/dashboard`, `/animals`, `/feed-board`, ...) is gated by `requireVolunteer()` — real Clerk sign-in — but `volunteer-ops`'s Clerk accounts all have `skipPasswordRequirement: true` (no password strategy at all), signed in instead via `@clerk/testing`'s testing-token mechanism (`clerk.signIn({ page, emailAddress })`), the same one that app's own Playwright E2E suite uses (`tests/e2e/fixtures.ts`). `DomainPack.auth`'s shape (`loginUrl` + `username`/`password` + CSS selectors) assumes a conventional same-origin form — there's no login form here at all for those selectors to target.

**Fixed**: `DomainPack.customLogin?: (browser, targetBaseUrl) => Promise<DomainPackStorageState>` (`src/types/domain-pack.ts`) — a generic, app-agnostic escape hatch alongside `auth`, not a Clerk-specific addition to core. Same once-per-run timing and failure-handling contract `auth` already had (`runDiscovery` calls it once before the worker pool starts, crashes the whole run on failure, still tears down). Mutually exclusive with `auth` — declaring both throws `ConflictingAuthConfigError` before the run starts (same timing as `InvalidConcurrencyCapError`/`assertDataPolicyAllowed`), since there's no sensible precedence rule to guess at. `packs/horse-haven-ops/domain-pack.ts` implements it with `@clerk/testing/playwright`'s `clerkSetup()` + `clerk.signIn()`, authenticating a dedicated Clerk-backed `VOLUNTEER`-role test identity provisioned by a new `volunteer-ops/scripts/seed-drover-test-clerk-volunteer.ts` (mirrors that repo's own `tests/e2e/global-setup.ts` pattern — `findOrCreateClerkUser` + upsert `Volunteer` by `clerkId`, never reusing the E2E suite's own `TEST_USERS`). New Drover-side env vars `HHOPS_CLERK_SECRET_KEY`/`HHOPS_CLERK_PUBLISHABLE_KEY` (copied from `volunteer-ops/.env`'s Clerk dev-instance keys) and `HHOPS_CLERK_TEST_EMAIL`.

**A real, non-hypothetical integration bug found and fixed getting this to work the first time**: `clerkSetup({ secretKey, publishableKey })` accepts explicit options and worked fine, but `clerk.signIn({ emailAddress, page })`'s email-based strategy has no options param for the secret key at all — its own source reads `process.env.CLERK_SECRET_KEY` directly, unconditionally. The first real attempt threw `"CLERK_SECRET_KEY environment variable is required for email-based sign-in"` immediately after `clerkSetup` had already succeeded with the explicit option — confirmed by reading `@clerk/testing`'s built source (`node_modules/@clerk/testing/dist/playwright/index.mjs`). Fixed by having `clerkCustomLogin` set `process.env.CLERK_SECRET_KEY = secretKey` itself before calling `clerk.signIn` — a real, if minor, "the library's two functions don't share the same configuration surface" gotcha worth knowing if `@clerk/testing` gets used anywhere else in this codebase later.

**Validated end-to-end, not just wired up**: a small 4-session smoke run (`orgSize 4`, 1 week, 1 session/week — one session per persona, `runs/hhops-5-smoke.sqlite`) completed 4/4 with zero in-session findings, including one session each on the two new authenticated goals (`view-dashboard`, `check-feed-board`) — confirmed genuine checkpoint success, not just "didn't crash" (an unreached checkpoint would show as an `action-budget-exhausted` finding, and the findings table came back empty). `browse-animals` wasn't drawn in this small a sample; not yet exercised. Real cost: $0.0233 total (first attempt, the `CLERK_SECRET_KEY` failure, cost $0 — it crashed before any session opened, per `auth`/`customLogin`'s shared "login failure crashes before any session starts" design working exactly as intended).

**What this doesn't yet close**: `packs/horse-haven-ops/domain-pack.ts`'s new goals are all read-only views (no data mutation, so `teardown` needed no changes) and all reachable by a single `VOLUNTEER`-role identity — `/admin`, `/training`, `/events`, and the volunteer's own `/checkin` self-service flow remain untested, and a pack needing multiple roles/accounts in one run still isn't supported (same limitation `auth` already had, just inherited by `customLogin` too). Not yet exercised at full `sim.config.ts` scale, only the small smoke config (`sim.config.smoke.ts`, new — a reusable small-scale config for future mechanical validation before committing to a full paid run).

## 2026-07-28 (3) — `packs/horse-haven-ops/domain-pack.ts`'s teardown silently deleted 0 rows on a non-UTC-timezone machine — RESOLVED 2026-07-28

Found while running the real validation pass for the "(2)" entry below (dedicated Drover Postgres container) — the very first two clean discovery runs against the new container both logged `[teardown] cleared 0 CheckIn row(s)`, even though the sessions had visibly checked in and out (`SELECT count(*) FROM "CheckIn" WHERE "volunteerId" = ...` showed 6 rows after a run whose teardown claimed 0 deleted). Root cause: `CheckIn.createdAt` is Prisma's plain `DateTime` (Postgres `timestamp` **without** time zone) — Prisma's own adapter writes/reads it as literal UTC wall-clock digits, but the teardown hook's raw `pg.Client` query bound plain JS `Date` objects as its `BETWEEN` parameters, and node-postgres's default serialization for a `Date` parameter formats it using the **local system timezone** (this machine: `America/New_York`, UTC-4) rather than UTC. So a real UTC instant like `2026-07-29T00:17:24.303Z` got sent to Postgres as the literal string `2026-07-28 20:17:24.303` — 4 hours off from the `00:17:...` wall-clock value Prisma had actually written — and the `BETWEEN` window silently matched nothing. Confirmed directly: re-running the identical `DELETE` with the Date objects replaced by `.toISOString()` strings (cast `::timestamp`, so Postgres takes the digits literally and discards the trailing `Z` rather than converting) matched all 6 rows correctly.

This is environment-dependent, not container-dependent — it would have silently no-op'd against the *old* shared container too, on this same machine, any time local wall-clock time isn't UTC. Whether it silently no-op'd during the "proven working... real CheckIn rows created and toggled correctly" 2026-07-28 run this doc's `ENVIRONMENT.md` describes is unverified after the fact (that claim was about the actor loop reaching checkpoints, not about confirming teardown's row count against a direct query) — worth treating with suspicion rather than assumed correct.

**Fixed**: `packs/horse-haven-ops/domain-pack.ts`'s teardown now converts `ctx.runStartedAt`/`ctx.runEndedAt` to `.toISOString()` strings before binding them, and casts both bind params `::timestamp` in the query, matching exactly what Prisma itself writes regardless of the host machine's local timezone. Verified end-to-end: a real discovery run's teardown log went from `cleared 0 CheckIn row(s)` (pre-fix, rows left behind) to `cleared 6 CheckIn row(s)` (post-fix, same run shape), and a direct post-run query confirmed the table back at 0 rows for the test volunteer.

**Worth generalizing**: any future domain-pack teardown hook that runs a raw SQL query against a Prisma-managed Postgres table for timestamp-window correlation (the exact pattern `CLAUDE.md`'s "Domain pack teardown hooks" section documents as one of the two sanctioned self-correlation strategies) needs to either bind ISO strings instead of `Date` objects, or explicitly `SET TIME ZONE 'UTC'` on the connection — a plain `Date` object bound to a raw `pg` query against a non-`timestamptz` column is not safe by default. Worth a callout in `CLAUDE.md`'s domain-pack-authoring guidance once a second real pack needs this pattern.

## 2026-07-28 (2) — Drover reuses volunteer-ops's own test-suite Postgres container, creating a collision risk — RESOLVED 2026-07-28

Found while doing Session 9 prep work: the container both `KIOSK.md` (superseded) and `packs/horse-haven-ops/ENVIRONMENT.md` pointed Drover at — `volunteer-ops/docker-compose.test.yml`, `localhost:5433`, db `volunteer_ops_test` — wasn't infrastructure built for Drover. It was `volunteer-ops`'s own vitest/Playwright E2E-suite database, reused as-is because it was already there and already worked.

That reuse was a real, live coupling, not a hypothetical one: `volunteer-ops/package.json`'s `test:db:down` runs `docker compose -f docker-compose.test.yml down -v` — a full teardown, no scoping to "only if nothing else is using it." A Drover validation run active at the same moment someone runs the real E2E suite (or `test:db:down`/`test:db:reset` by hand) would silently destroy one or the other's data or the container itself mid-run.

**Fixed**: gave Drover a fully separate container, decoupled from `volunteer-ops`'s CI infrastructure entirely, mirroring the existing `test:db:*` shape one-for-one so the pattern stays instantly recognizable:

- `volunteer-ops/docker-compose.drover.yml` — same `postgres:16-alpine` image and `tmpfs` mount as `docker-compose.test.yml`'s `test-db` service, but its own service name (`drover-db`), its own port (`5434`, not `5433`), and its own database (`volunteer_ops_drover`, not `volunteer_ops_test`) — both containers now run simultaneously with zero contention (confirmed: both were up at once during validation).
- `volunteer-ops/.env.drover.example` (committed) / `.env.drover` (gitignored, same `!.env.drover.example` exception pattern `.env.test.example` already used) — same two-var `DATABASE_URL`/`DIRECT_URL` shape, pointed at `localhost:5434/volunteer_ops_drover`.
- New npm scripts in `volunteer-ops/package.json`, mirroring `test:db:*` one-for-one: `drover:db:up`, `drover:db:down`, `drover:db:migrate`, `drover:db:seed`, `drover:db:reset`, plus `drover:seed-volunteer` (`dotenv -e .env.drover -- tsx scripts/seed-drover-test-volunteer.ts` — this script and the npm command to run it existed as a name only before this fix; the actual script now matches).
- `scripts/seed-drover-test-volunteer.ts`'s `config({ path: ".env.test" })` → `config({ path: ".env.drover" })`, guard message updated to match.
- `Drover/.env`'s `HHOPS_TEST_DATABASE_URL` moved to `postgresql://postgres:postgres@localhost:5434/volunteer_ops_drover`.
- `packs/horse-haven-ops/ENVIRONMENT.md` relocated from the repo root (`Drover/ENVIRONMENT.md`, where it had been left instead of under `packs/`, despite its own text already claiming the `packs/<app>/ENVIRONMENT.md` convention) and rewritten to reference `docker-compose.drover.yml`/`.env.drover`/`drover:db:*` throughout; its "Known limitation — shared test container" section (the one this entry closes) is deleted. `KIOSK.md` (root), which `ENVIRONMENT.md` already described itself as superseding, is deleted for the same reason.

**Validated end-to-end**, not just wired up: ran `drover:db:up` → `drover:db:migrate` → `drover:db:seed` → `drover:seed-volunteer` against the new container while the old `volunteer-ops-test-db-1` container (5433) stayed running the whole time with zero interference; booted the app server bound to `.env.drover`, confirmed `/kiosk` reachable with no auth wall; ran a full `drover run`/`analyze`/`report` pass (24/24 sessions, real cost $0.1484 actor + $0.0170 analyst) against it. One real snag hit along the way, **not** a container problem: the first attempt's `npm run start` silently failed with `EADDRINUSE` (a stale `next start` process from earlier the same day was already bound to port 3000 against the *old* 5433 container) and Drover's own run happily proceeded against that stale/wrong-DB server without any error, since nothing in the pipeline checks which app instance is actually listening — see the new "(3)" entry above for the second, independent bug (a teardown timezone bug) that first run's confusion led to discovering. Killed the stale process, restarted correctly, re-verified via a real browser checkin against the new container's own seeded code before trusting any further run. Final state: 0 leftover rows in the dedicated container's `CheckIn` table after the last run's teardown.

**Worth generalizing**: `CLAUDE.md`'s "Writing a domain pack" guidance should note this as the standing convention — every domain pack targeting a real app should provision its own dedicated, disposable environment for that app rather than reusing whatever test infrastructure the app's own repo happens to already have, even when reuse is tempting and "already works." Also worth a callout for anyone repeating this exercise: **explicitly check what's already listening on the target port before trusting that a freshly-started app server is the one actually being tested** — an `EADDRINUSE` on `npm run start` is silent unless the log is actually read, and Drover has no way to detect it's talking to the wrong backend.

## 2026-07-28 — actor tier's click/fill selectors were CSS strings guessed from an ARIA role tree, not real CSS — RESOLVED 2026-07-28

Found while investigating the first real Horse Haven Ops kiosk validation run (`runs/hhops-1.sqlite` — see `KIOSK.md`): 19 of 24 sessions hard-stopped or exhausted their action budget on a single-field kiosk form (`src/app/kiosk/page.tsx` in `volunteer-ops` — one plain `<input placeholder="Check-in code">`, nothing exotic). Root cause: `capturePerception` (`src/actor/loop.ts`) showed the model an ARIA role/accessible-name tree (`page.locator("body").ariaSnapshot()`, default mode — no CSS-derivable detail at all: no tags, ids, or classes), while the `decide_action` tool schema (`src/actor/provider.ts`) told the model `selector` must be "CSS selector of the element." The model had no way to bridge the two and predictably guessed invented syntax like `textbox[placeholder="Check-in code"]` (not real CSS — no `<textbox>` tag exists) or bare `textbox` (parsed as a CSS type selector for a nonexistent tag), either of which burns Playwright's full 30s default timeout before failing. A few sessions only succeeded by accident, when the model padded a comma-separated fallback list with real CSS (`input[placeholder*="code" i]`) alongside the fake syntax.

**Fixed**: switched the actor tier to Playwright's own purpose-built solution for this — `ariaSnapshot({ mode: "ai" })` (available since Playwright ~1.48, already the pinned 1.61.1 here), which annotates each element with a stable `[ref=eN]`. The model is now told (prompt + tool schema) to copy that ref back verbatim; `executeAction` (`src/actor/loop.ts`) builds the actual Playwright locator as `aria-ref=${ref}` before calling `BrowserSession.click`/`.fill` (`src/browser/session.ts`), which forward it straight into `page.locator()` unchanged — no CSS guessing anywhere in the path anymore. Folded into the same fix, per two follow-on risks the ref-based approach introduces that a straight port would have missed:

- **Ref freshness across retries.** A ref only resolves against the exact snapshot generation it came from (confirmed empirically: re-navigating the same page invalidates a ref taken before the reload). `capturePerception` was already called fresh once per outer while-loop iteration, but the *retry* loop (up to `maxRetries` attempts on a single failed decision) reused one perception/prompt across every attempt — safe today only because a thrown click/fill error implies the DOM didn't actually change, but fragile reasoning to depend on long-term. Moved perception capture inside the retry loop itself, so every `decide()` call — first attempt or retry — always acts on a ref taken from the page as it looks right now. Bonus: a retry's prompt now also includes the `[error] previous attempt failed...` history line from the prior attempt, which it previously didn't see until the *next* outer iteration.
- **Fail-fast on a bad ref.** A malformed or stale ref is now a real bug signal, not a guess worth patiently waiting out — `BrowserSession.click`/`.fill` pass an explicit `{ timeout: 5000 }` (`REF_ACTION_TIMEOUT_MS`) whenever the selector is `aria-ref=`-prefixed, instead of Playwright's 30s default. Verified directly against a real page: a nonexistent ref now fails at exactly the configured timeout, not 30s.
- **Defensive parsing**: `normalizeRef` (`src/actor/loop.ts`) extracts the `e\d+` token from whatever the model returns, in case it echoes back `[ref=e4]` or `ref=e4` instead of the bare `e4` the prompt asks for.

Test coverage: `tests/actor/loop.test.ts`'s click/fill-exercising cases now compute real refs via a `refFor` test helper (a fresh `body`-rooted `ariaSnapshot({mode:"ai"})`, matching `capturePerception` exactly — an isolated per-element snapshot numbers refs from a different root and returns the wrong value, a real mistake made and caught while writing this fix's own tests) instead of hardcoding CSS selectors; the hard-stop test uses a made-up, never-issued ref (`"e9999"`) to exercise the new fail-fast timeout directly. `tests/browser.test.ts` (the primitive's own generic-CSS test coverage) was left untouched — `BrowserSession.click`/`.fill` only special-case the short timeout for `aria-ref=`-prefixed selectors, so they stay usable with a plain CSS string for any other caller. 229 tests passing (no new test files, several existing ones rewritten).

**What this doesn't fix**, worth its own entry if it turns out to matter:
- **Event-log/report readability regression.** `ActionEvent.target` for a click/fill is now `aria-ref=e4` instead of a human-readable CSS string like `button:has-text("Check In / Out")` — a real trade-off accepted for reliability. The per-action `reasoning` sentence is the only human-readable context left in the trace for a click/fill; worth revisiting (e.g. also logging the element's accessible name/role alongside the ref) if report evidence appendices turn out to need more.
- **Never re-run against the real Horse Haven Ops kiosk yet.** This fix is verified by unit/integration tests and manual real-browser verification of the ref mechanics (empirically confirmed: refs are stable across page reloads when read from the same `body`-rooted snapshot root, and a bad ref fails at exactly its configured timeout), but the actual `runs/hhops-1.sqlite`-style validation run hasn't been repeated with this fix in place — that's the real proof this raises the ~21% success rate, and is the natural next step.

## 2026-07-26 — no `SimConfig`/`DomainPack` path calls the treeLine adapter's `performLogin`, so every persona is locked out of anything behind an auth wall — RESOLVED 2026-07-26

Found while auditing what's needed for Session 9's real Horse Haven Ops domain pack (`CLAUDE.md`, `SESSION-LOG.md`'s "ad hoc... first real-app validation run" entry). `src/treeline/adapter.ts` already exposes `performLogin` (returns a Playwright `storageState`), and `BrowserSession` (`src/browser/session.ts`) already accepts one via `opts.storageState` — both halves of the plumbing exist, built independently in earlier sessions, but nothing in `SimConfig`, `DomainPack`, or `runDiscovery` (`src/orchestrator/run-discovery.ts`) ever calls the former or threads its result into the latter. Confirmed directly against a real target: the existing `packs/horse-haven-ops/` domain pack can only reach `/kiosk` (the one route in that app with no `requireVolunteer()` auth wall) — every other real Horse Haven Ops flow (dashboard, animals, feed board, admin) needs a signed-in session Drover currently has no way to establish.

**Fixed**: `DomainPack.auth?: DomainPackAuthCredentials` (`src/types/domain-pack.ts`) — see `CLAUDE.md`'s Orchestrator section for the full as-built detail. `runDiscovery` calls `performLogin` once per run (before the worker pool starts) and threads the resulting `storageState` into every session's `BrowserSession.open()`. Credential values are the pack author's own responsibility (env vars read at module-load time, same precedent `teardown`'s `HHOPS_TEST_DATABASE_URL` already set), and `auth` lives on `DomainPack` specifically so it never round-trips through `Run.config` into the SQLite database (only `SimConfig` is persisted there). Test coverage: `tests/orchestrator/run-discovery.test.ts` gained two cases — login called exactly once and its `storageState` reaching every session's `BrowserSession.open()` call (spied), and a login failure crashing the whole run with teardown still firing.

**What this doesn't yet close**, worth its own future entry once a real multi-role pack needs it:
- **One credential set per run, not per persona/goal.** A pack whose different goals genuinely need different roles/accounts (e.g. Horse Haven Ops' `ADMIN` vs. `VOLUNTEER` vs. `SHIFT_LEAD` vs. `KIOSK`) can't express that yet — every session in a run shares the one `storageState` `domainPack.auth` produces. Extending to per-persona credentials would need a `DomainPack`-level map (persona id → credentials) analogous to `goalWeightsByPersona`, not a change to the generic, app-agnostic `PersonaArchetype` type.
- **Never exercised against a real login** — every test/run so far has used a mocked `treelineAdapter.performLogin`. The real `RealTreelineAdapter.performLogin` delegates straight to `@treeline/acquire`'s own implementation, unverified end-to-end here (same "unverified against real infra" shape as `OllamaModelProvider` and the analyst tier's `countTokens` path).
- **`packs/horse-haven-ops/domain-pack.ts` still only covers the kiosk flow** — this fix removes the *technical* blocker to reaching auth-walled routes, but the pack itself hasn't been extended with real goals/checkpoints for `/dashboard`, `/animals`, `/feed-board`, etc. yet. That's the remaining Session 9 work.

## 2026-07-25 (test coverage sweep) — two code-shape observations found while auditing test coverage — RESOLVED 2026-07-25

Not test gaps (tracked in the new `TESTING-GAPS.md` instead) — these are two small behavioral/shape questions about the actual code, noticed while reading every file against its tests. Logged per this file's own instruction rather than fixed at the time, since that pass was scoped to tests only. Both resolved in a follow-up pass same day:

- **`executeAction`'s `"finish"` case (`src/actor/loop.ts`) was unreachable.** Confirmed: `runPersonaSession`'s own loop already checks `decision.actionType === "finish"` and `break outer`s before `executeAction` is ever called, and no other caller exists. A few other v1 scope cuts, each deliberate but worth knowing:
- No wall-clock safety ceiling on a stampede run — unlike the actor/analyst tiers' dollar budget ceilings, there's no LLM cost to bound, so nothing currently stops a very large `--iterations-per-worker` against a slow site from running for a long time. A future `maxDurationMs` cutoff (stop early, report partial results) would close this the same way the dollar ceilings close the equivalent risk elsewhere.
- Only a discovery run's `navigate` targets get replayed, never `click`/`fill` sequences — deliberate (CONTEXT.md frames Stampede as "response time percentiles... per route," and replaying full data-mutating goal sequences at load-test volume with no teardown correlation would leave garbage staging data behind), but means Stampede can't yet load-test a flow that only becomes slow a few clicks deep (e.g. a slow POST after a multi-step form). Extending this would need its own teardown-correlation story first, not just an engine change.
- `runStampede` only exercises one `deviceType` per invocation (default `desktop`) — no built-in way to compare mobile vs. desktop load characteristics in one run yet.
- `DEFAULT_CONCURRENCY_LEVELS` (`[1, 5, 10]`) and `DEFAULT_ITERATIONS_PER_WORKER` (`3`) are both guesses, same "not derived from real run data" caveat as the analyst tier's `DEFAULT_SESSIONS_PER_CHUNK` — revisit once a real Horse Haven Ops Stampede run shows what's actually useful.

## 2026-07-23 (S4) — Domain pack teardown hooks have no record of what a run created — PARTIALLY ADDRESSED 2026-07-25

`DomainPack.teardown` (added this session, `src/types/domain-pack.ts` — not in CONTEXT.md's verbatim schema, see `SESSION-LOG.md`'s Session 4 entry) was called with only `{ runId, targetBaseUrl }`. It has no list of the actual records/rows a run's personas created (signups, schedule edits, etc.) — CONTEXT.md's "staging teardown wipes everything a run created" assumes the pack author has _some_ way to correlate created data back to a run. As built, that correlation was entirely the pack author's responsibility, via one of two strategies: tagging synthetic form data with the runId at fill-time, or a timestamp-window sweep.

Fixed the half of this that Drover could actually fix without a real domain pack to learn from: **`DomainPackTeardownContext` now also carries `runStartedAt`/`runEndedAt`** (epoch ms — `runEndedAt` is `Date.now()` taken at the teardown call site itself, since the run row's own `endedAt` isn't written until after teardown returns). This makes the timestamp-window sweep strategy actually usable — before this, a pack author couldn't even implement it without opening their own separate SQLite connection just to read the run's own timing back, since teardown gets no `db` handle. The runId-tagging strategy needed nothing further from Drover and was never blocked.

**Deliberately not attempting a fuller fix** (e.g., Drover tracking every app-side record a run touched): there's no real mechanism available to do this generically without either (a) requiring every domain pack to report back what it created, which is just a different, more invasive version of the same self-correlation burden, or (b) Drover inspecting response bodies/DOM state to infer created records, which is real scope creep beyond what CONTEXT.md asks for. Whether `runId` + a timestamp window is actually *sufficient* for a real teardown — or whether some apps' data shapes make a sweep genuinely ambiguous (e.g. two runs overlapping in time under concurrency, or records with no reliable created-at column) — is still unverified until the Horse Haven Ops domain pack (Session 8/9 scope) is built and has to write a real one.
