# GAPS.md — Drover's own blind spots

Drover shortcomings, missing capabilities, and future-improvement ideas, logged as they surface during builds and real runs (per CONTEXT.md's Learning Loop). Entries here are candidates for post-v1 work — log and move on, don't fix out of scope.

## 2026-07-25 (test coverage sweep) — two code-shape observations found while auditing test coverage

Not test gaps (tracked in the new `TESTING-GAPS.md` instead) — these are two small behavioral/shape questions about the actual code, noticed while reading every file against its tests. Logged per this file's own instruction rather than fixed, since this pass was scoped to tests only.

- **`executeAction`'s `"finish"` case (`src/actor/loop.ts`, the `switch` around line 62) looks unreachable.** `runPersonaSession`'s own loop already checks `decision.actionType === "finish"` and `break outer`s (around line 211) *before* `executeAction` is ever called — so the `case "finish": return undefined;` branch inside `executeAction` has no caller path that can reach it. Either there's a code path that can still hand a `"finish"` decision to `executeAction` that isn't obvious from a read-through, or this is dead defensive code left over from an earlier shape of the loop. Worth a second look before deciding whether to delete it or whether it's actually load-bearing.
- **`page-error` events never become an in-session finding.** `BrowserSession` (`src/browser/session.ts`) wires a `pageerror` listener that logs an uncaught JS exception as a `page-error` observation event, same as `console-error`/`http-failure`. But `detectAndRecordFindings` (`src/actor/loop.ts`) only checks newly-seen events for `actionType === "console-error"` or `actionType === "http-failure"` — a `page-error` event is recorded in the raw event log but can never trigger a finding, unlike its two siblings. CONTEXT.md's in-session finding list doesn't mention `page-error` either, so this may be intentional (maybe uncaught exceptions reliably also fire a console error in practice, making it redundant) — but it reads like an omission rather than a documented decision. Worth deciding deliberately one way or the other.

## 2026-07-25 (S7) — Stampede results aren't folded into `drover report`, and a few v1 scope cuts are worth revisiting

`drover stampede` (`src/stampede/`) writes its own `stampede_runs`/`stampede_route_results` tables and prints a console table, but `buildRunReport`/`renderMarkdownReport` (`src/report/`) don't know these tables exist yet — a stampede run's percentiles/error rates have to be read directly from SQLite or the CLI's console output, not the markdown report. Natural follow-up once a real domain pack's Stampede runs are routine: a "Load test results" section in the report, keyed off the discovery run id a stampede run references.

A few other v1 scope cuts, each deliberate but worth knowing:
- No wall-clock safety ceiling on a stampede run — unlike the actor/analyst tiers' dollar budget ceilings, there's no LLM cost to bound, so nothing currently stops a very large `--iterations-per-worker` against a slow site from running for a long time. A future `maxDurationMs` cutoff (stop early, report partial results) would close this the same way the dollar ceilings close the equivalent risk elsewhere.
- Only a discovery run's `navigate` targets get replayed, never `click`/`fill` sequences — deliberate (CONTEXT.md frames Stampede as "response time percentiles... per route," and replaying full data-mutating goal sequences at load-test volume with no teardown correlation would leave garbage staging data behind), but means Stampede can't yet load-test a flow that only becomes slow a few clicks deep (e.g. a slow POST after a multi-step form). Extending this would need its own teardown-correlation story first, not just an engine change.
- `runStampede` only exercises one `deviceType` per invocation (default `desktop`) — no built-in way to compare mobile vs. desktop load characteristics in one run yet.
- `DEFAULT_CONCURRENCY_LEVELS` (`[1, 5, 10]`) and `DEFAULT_ITERATIONS_PER_WORKER` (`3`) are both guesses, same "not derived from real run data" caveat as the analyst tier's `DEFAULT_SESSIONS_PER_CHUNK` — revisit once a real Horse Haven Ops Stampede run shows what's actually useful.

## 2026-07-24 (S6) — Report structure hasn't been validated against a real multi-run dataset or user feedback

`drover report`'s markdown structure (findings summary → breakdown by flow → run metadata → since-last-run counts → evidence appendix) was decided directly from CONTEXT.md's "Reporting" section and the prior session's own Session 6 spec (see `SESSION-LOG.md`), not from showing a sample to the user first — that spec flagged a user round-trip as a nice-to-have, explicitly optional if it didn't happen before the work landed, and it didn't happen here. It's also only been exercised against small hand-built fixture data (unit tests, one manual smoke run) — never a real multi-week, multi-persona Horse Haven Ops run with dozens of sessions and a mix of resolved/still-open/new findings across several `drover run`/`drover analyze` cycles. Worth a real structure/readability pass once the Horse Haven Ops domain pack (Session 8/9 scope) produces a real run to report on — likely candidates for change: whether the findings summary table needs pagination/truncation for a run with many unique match_keys, and whether "breakdown by flow" duplicating full rows per goal (rather than just listing match_keys) gets unwieldy for a finding that touches many goals.

## 2026-07-23 (S4) — Domain pack teardown hooks have no record of what a run created

`DomainPack.teardown` (added this session, `src/types/domain-pack.ts` — not in CONTEXT.md's verbatim schema, see `SESSION-LOG.md`'s Session 4 entry) is called with only `{ runId, targetBaseUrl }`. It has no list of the actual records/rows a run's personas created (signups, schedule edits, etc.) — CONTEXT.md's "staging teardown wipes everything a run created" assumes the pack author has _some_ way to correlate created data back to a run. As built, that correlation is entirely the pack author's responsibility (e.g., tagging synthetic form data with the runId at fill-time, or a timestamp-window sweep) — Drover doesn't track "which app-side records this run touched" anywhere. Worth revisiting once a real domain pack (Session 8's Horse Haven Ops pack) actually needs to implement a non-trivial teardown and finds out whether `runId` alone is enough.
