# GAPS.md — Drover's own blind spots

Drover shortcomings, missing capabilities, and future-improvement ideas, logged as they surface during builds and real runs (per CONTEXT.md's Learning Loop). Entries here are candidates for post-v1 work — log and move on, don't fix out of scope.

## 2026-07-24 (S6) — Report structure hasn't been validated against a real multi-run dataset or user feedback

`drover report`'s markdown structure (findings summary → breakdown by flow → run metadata → since-last-run counts → evidence appendix) was decided directly from CONTEXT.md's "Reporting" section and the prior session's own Session 6 spec (see `SESSION-LOG.md`), not from showing a sample to the user first — that spec flagged a user round-trip as a nice-to-have, explicitly optional if it didn't happen before the work landed, and it didn't happen here. It's also only been exercised against small hand-built fixture data (unit tests, one manual smoke run) — never a real multi-week, multi-persona Horse Haven Ops run with dozens of sessions and a mix of resolved/still-open/new findings across several `drover run`/`drover analyze` cycles. Worth a real structure/readability pass once the Horse Haven Ops domain pack (Session 8/9 scope) produces a real run to report on — likely candidates for change: whether the findings summary table needs pagination/truncation for a run with many unique match_keys, and whether "breakdown by flow" duplicating full rows per goal (rather than just listing match_keys) gets unwieldy for a finding that touches many goals.

## 2026-07-23 (S4) — Domain pack teardown hooks have no record of what a run created

`DomainPack.teardown` (added this session, `src/types/domain-pack.ts` — not in CONTEXT.md's verbatim schema, see `SESSION-LOG.md`'s Session 4 entry) is called with only `{ runId, targetBaseUrl }`. It has no list of the actual records/rows a run's personas created (signups, schedule edits, etc.) — CONTEXT.md's "staging teardown wipes everything a run created" assumes the pack author has _some_ way to correlate created data back to a run. As built, that correlation is entirely the pack author's responsibility (e.g., tagging synthetic form data with the runId at fill-time, or a timestamp-window sweep) — Drover doesn't track "which app-side records this run touched" anywhere. Worth revisiting once a real domain pack (Session 8's Horse Haven Ops pack) actually needs to implement a non-trivial teardown and finds out whether `runId` alone is enough.
