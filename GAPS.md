# GAPS.md — Drover's own blind spots

Drover shortcomings, missing capabilities, and future-improvement ideas, logged as they surface during builds and real runs (per CONTEXT.md's Learning Loop). Entries here are candidates for post-v1 work — log and move on, don't fix out of scope.

## 2026-07-24 (post-S5, GAPS fix) — Checkpoint reach times are keyed by opaque checkpoint id, with no description/ordering context

Previously logged as "Analyst tier doesn't yet consume the now-populated `ActionEvent.checkpointId`." `src/analyst/digest.ts`'s `buildSessionDigest` now computes `checkpointReachTimesMs: Record<checkpointId, elapsedMs>` per session (first event tagged with each checkpoint id, elapsed since session start), and `src/analyst/prompt.ts` surfaces it in each session's digest block as "Checkpoint reach times" — giving the analyst true per-checkpoint latency to compare across sessions sharing a `goalId`, instead of the old whole-session-`totalDurationMs`-by-`goalId` proxy (which is still used as-is for the "abnormally high action count" half of `slow-checkpoint`; only the latency half changed). This didn't need passing `Goal`/`Checkpoint` definitions into the digest as originally assumed — `runAnalyst` only has the run's `SimConfig` snapshot (not the domain pack), but the checkpoint *id* alone, already on `ActionEvent`, is enough to group and compare reach times across sessions without needing the checkpoint's human-readable description or its position in the goal's checkpoint list. Covered by two new cases in `tests/analyst/digest.test.ts` (first-reach-wins when tagged twice; empty record when no event is tagged). What's still open: the analyst only ever sees a checkpoint's opaque id string (whatever a domain-pack author chose, e.g. `"cp-signup-complete"`) with no description or ordering — it has to infer meaning from the id itself, since the digest has no access to the original `Checkpoint.description` or its position within `Goal.checkpoints`. Post-v1: if a real domain pack's checkpoint ids aren't self-descriptive enough for the analyst to reason about usefully, either store a `Run`-scoped id→description map at run-creation time, or have `drover analyze` optionally accept the domain-pack path (mirroring `drover run`'s `--config`) purely to enrich this context.

## 2026-07-24 (post-S5, GAPS fix) — Analyst-tier budget ceiling is a pre-flight estimate, not exact accounting

Previously logged as "No budget enforcement for the analyst tier." `runAnalyst` (`src/analyst/analyze.ts`) now supports an optional `budget.analystCeilingUsd` (`src/types/config.ts`): if set, `estimateAnalystCostUsd` (`src/analyst/budget.ts`) computes a worst-case cost from the assembled system/user prompt length (chars/4 as a token proxy — no real tokenizer dependency) and the Batch call's `max_tokens` ceiling, applies the same `BATCH_DISCOUNT` the real call would get, and throws `AnalystBudgetExceededError` *before* `provider.analyze()` is ever invoked if the estimate exceeds the ceiling — a Batch request is billed the moment it's submitted, so a post-hoc cap (checked after the call, like `SessionBudget`) couldn't actually prevent overspend on that same call the way it can for a multi-action persona session. Unset `analystCeilingUsd` preserves the old no-cap behavior exactly. Covered by `tests/analyst/budget.test.ts` and three new cases in `tests/analyst/analyze.test.ts`. What's still open: the chars/4 estimate is a heuristic, not the real tokenizer Anthropic bills against, so it can over- or under-estimate actual cost (deliberately biased toward over-estimating, to fail closed rather than silently blow past a ceiling); and splitting a very large run's sessions into multiple smaller batch requests (CLAUDE.md's other suggested mitigation) still isn't implemented — the whole run's digests still go into one prompt. Post-v1: swap in a real tokenizer if the heuristic proves too imprecise on a real domain pack, and revisit chunking if one run's session count ever makes a single prompt unwieldy regardless of cost.

## 2026-07-23 (post-S5, GAPS fix) — `concurrencyCap` above 1 is still not real concurrency, just rejected cleanly

Previously logged as "`concurrencyCap` config field has no effect yet" (silent no-op). `runDiscovery` (`src/orchestrator/run-discovery.ts`) now calls `assertConcurrencyCapSupported` before doing anything else — a `concurrencyCap > 1` throws `ConcurrencyNotImplementedError` instead of being silently ignored (same timing/pattern as `assertDataPolicyAllowed`; covered by a new `run-discovery.test.ts` case). This closes the "silent no-op" half of the original gap. What's still open: there is still no actual bounded-concurrency execution path — a pack author who wants real parallelism has no option, only a clear error telling them it isn't built. Post-v1: implement bounded concurrency (a worker-pool-style scheduler over `buildSchedule`'s output, respecting per-session isolation and the run-level budget ceiling) and only then relax the guard.

## 2026-07-23 (S3) — No local/self-hosted provider for `restricted` domain packs

CONTEXT.md's "Data routing & privacy" names a fully local model (via Ollama) as the zero-exposure actor-tier option for `restricted` domain packs when cost is a concern beyond staying on Anthropic. Session 3 only implements `AnthropicModelProvider`; `assertDataPolicyAllowed`'s approved-provider set for `restricted` packs is just `["anthropic"]` (`src/actor/provider.ts`). Adopters with a real `restricted` app and no Anthropic budget have no provider to route to yet. Post-v1: add an Ollama-backed `ModelProvider` implementation and add `"ollama"` to the approved set once it exists.

## 2026-07-23 (S3) — Checkpoint detector DSL is intentionally minimal

`src/actor/checkpoint.ts`'s three matchers (`url:`, `selector:`, `text:`) are substring/existence checks only — no regex, no visibility vs. presence distinction, no combining multiple conditions into one checkpoint (AND/OR). Fine for the toy example and Session 3's tests; Session 8's real Horse Haven Ops pack may need one of these and should extend the DSL then rather than working around it with extra checkpoints.

## 2026-07-23 (S3) — Persona trait numeric range isn't specified in CONTEXT.md

CONTEXT.md types `patience`/`techSavviness` as `number` with no documented range. Session 3 assumed 0..1 normalized (`src/actor/prompt.ts` techSavviness bucketing, `src/actor/loop.ts` patience → retry cap and pacing delay). This needs to be codified explicitly in Session 8's domain-pack authoring guide so pack authors don't guess a different scale (e.g. 1-10).

## 2026-07-24 (post-S5, GAPS fix) — `drover run`'s reconciliation pass no longer needs an ordering dependency on `drover analyze` to be correct

Previously logged as "Cross-run reconciliation is two-phase and can be transiently wrong for cross-session findings." `reconcileRunFindings` (`src/orchestrator/reconcile.ts`) gained a `ReconcileOptions.crossSessionDataComplete` flag (default `true`). `runDiscovery`'s post-run call now explicitly passes `crossSessionDataComplete: false`: at that point in the pipeline, `drover analyze` hasn't run yet, so `getCrossSessionFindingsByRun(runId)` is always empty by construction — not because the pattern actually stopped recurring. Previously this made the absent-match_key loop mark any prior open cross-session-typed match_key `resolved`, a tag that was only corrected later by `runAnalyst`'s second reconciliation call (relying on the S5 upsert fix to survive being written twice). Now the first pass simply skips cross-session-typed match_keys entirely (leaves them at whatever status they already had) when `crossSessionDataComplete` is false, so no premature `resolved` tag is ever written to `finding_status_history` in the first place, and the console summary `drover run` prints is accurate immediately rather than only after `drover analyze` also runs. In-session-typed match_keys are unaffected — those are fully known right after a run finishes, so they're still resolved/still-open/new'd in the same single pass as before. Covered by two new cases in `tests/orchestrator/reconcile.test.ts` ("leaves a prior open cross-session-typed match_key untouched when crossSessionDataComplete is false" / "still resolves an absent in-session-typed match_key even when crossSessionDataComplete is false"). What's still open: this only prevents *false* resolutions — it doesn't change the fact that a cross-session-typed match_key's `new`/`still-open` status still can't be assigned until `drover analyze` actually runs and re-detects the pattern (there's no data to tag it with before that). A domain pack that never runs `drover analyze` after `drover run` will simply never get cross-session findings reconciled at all, which is expected (analyze is what produces the data reconciliation acts on) but still worth flagging explicitly once Session 6's reporting work exists, per the original entry's suggestion.

## 2026-07-23 (S4) — Domain pack teardown hooks have no record of what a run created

`DomainPack.teardown` (added this session, `src/types/domain-pack.ts` — not in CONTEXT.md's verbatim schema, see BUILD-STATE.md decisions log) is called with only `{ runId, targetBaseUrl }`. It has no list of the actual records/rows a run's personas created (signups, schedule edits, etc.) — CONTEXT.md's "staging teardown wipes everything a run created" assumes the pack author has *some* way to correlate created data back to a run. As built, that correlation is entirely the pack author's responsibility (e.g., tagging synthetic form data with the runId at fill-time, or a timestamp-window sweep) — Drover doesn't track "which app-side records this run touched" anywhere. Worth revisiting once a real domain pack (Session 8's Horse Haven Ops pack) actually needs to implement a non-trivial teardown and finds out whether `runId` alone is enough.
